# AI 协作记录

本项目使用 AI 辅助实现和审查。Codex 负责代码、集成、测试和文档；Claude 通过真实 CLI 调用参与设计与实现审查。Claude 没有读取本地文件或运行工具，收到的是必要的设计背景和源码文本。

各轮均请求 `claude-opus-5-5`、`xhigh`，返回的实际模型标识与请求一致。CLI 未提供可独立核验的服务端推理强度，因此仅记录请求值，不声称已验证强度生效。

## 第一轮：设计审查

保留的原始回复：[round1-response.md](ai/round1-response.md)，调用元数据：[round1-metadata.json](ai/round1-metadata.json)。

采纳的建议：

- 地址集合使用规范化闭区间，IPv4 与 IPv6 保持分离。
- 避免通过枚举地址或机器整数计数处理 IPv6 全空间。
- 最大地址与零地址的相邻操作返回不存在，避免环绕。
- 使用 Python 参考模型、小空间点集和独立二叉前缀树验证，不仅检查几个演示结果。

经本地判断保留的不同选择：

- 使用四个 `UInt` 字表达地址，并测试每个 32 位进位／借位边界；未采纳两个 `UInt64` 的表示建议。
- CIDR 默认清除主机位，提供 `strict=true`；未采纳默认严格模式。此行为在 API、CLI、测试和文档中一致。

## 第二轮：实际源码审查

保留的原始回复：[round2-response.md](ai/round2-response.md)，调用元数据：[round2-metadata.json](ai/round2-metadata.json)。该轮输入为地址、CIDR、集合模块的实际源码及当时已验证的事实。

Claude 未提出带明确反例的高、中严重度问题，指出嵌入 IPv4 的非法 IPv6 输入可能只在错误载荷中保留 IPv4 尾段。例如 `::ffff:1.2.3.256` 原先返回尾段 `1.2.3.256`。

本地检查确认该现象。虽然错误文本不是稳定协议的一部分，仍将解析器改为保留完整原始地址，并增加错误载荷回归。还补充一次 `::` 仅压缩一个零组、45 字符混写输入、跨字边界范围分解、跨地址族最大值／零值分离等测试。

Claude 对 `UInt::ctz(0)` 和位操作语义的疑问由内部位掩码测试与实际编译目标测试检查。原始回复中的建议、未验证判断和当时测试数量属于审查时点信息；最终接口以 [SPEC.md](SPEC.md) 为准，最终实测以 [TESTING.md](TESTING.md) 和 CI 为准。
